# Design

> 配套：[`storage-and-cache.md`](./storage-and-cache.md)（持久化层、缓存语义、失效矩阵、观影记录与收藏）、[`content-catalog.md`](./content-catalog.md)（内容目录边界、后台采集调度、搜索改造）。
> 需求见 `specs/**`；动机见 `proposal.md`。

## Context

当前持久化状态（`app/src/main/java/com/libretv/tv/data/`）：

| 载体 | 内容 | 问题 |
|---|---|---|
| SP `libretv_sources` | 自定义源、removed / disabled 集合 | 无 schema 版本 |
| SP `libretv_settings` | 7 个布尔开关 | 无 schema 版本 |
| SP `libretv_watch_history` | JSON 数组，上限 40 条 | 整表读写，无法按影片聚合 |
| SP `libretv_search_history` | JSON 数组 | 同上 |
| SQLite `feed_cache.db` | 1 表 3 列，手工 `SQLiteOpenHelper` | `onUpgrade` 为 `DROP TABLE`（`FeedCacheDb.kt:100-103`），加一列即清空全部缓存 |

约束：

- `minSdk 23`、`targetSdk 34`、Kotlin 1.9.x（由 Compose compiler `1.5.14` 推断），无注解处理器；
- `domain/**` 不允许出现 `import android.`（架构重构 D2），因此持久化技术不得渗入领域层；
- 领域模型重构（`architecture-refactor` 变更）提供 `TitleGroup` / `SourceOffer` / `FeedCard` 契约，本变更依赖其落地；
- TV 设备：常驻供电、存储与带宽有限、无软键盘交互。

## Goals / Non-Goals

**Goals**

- 单一持久化层承载结构化数据与云端响应缓存，具备可测试的无损迁移；
- 缓存读取具备明确的三态语义，杜绝「先清空再填充」造成的闪屏；
- 内容元数据可离线读取，播放地址始终实时解析；
- 后台采集与用户请求在配额与并发上完全隔离；
- 领域层保持纯 Kotlin，持久化技术只出现在数据层。

**Non-Goals**

- 不做全量无界采集（存储、带宽、上游封禁三重不可行，详见 `content-catalog.md` §1）；
- 不做常驻前台服务；
- 不引入依赖注入框架与网络库；
- 不改变播放地址的解析时机与失败语义（属 `architecture-refactor` 范围）；
- 不引入跨设备同步（云端账号体系不在本变更范围）。

## Decisions

### D1 引入 Room，替代手写 SQLite 与 SharedPreferences

**选择**：`androidx.room` + KSP，Room 数据库作为唯一持久化入口；设置类偏好项仍保留 SharedPreferences。

**理由**：本变更把存储范围从「1 表 1 行 payload」扩大到「8 张表 + 跨表关系」，收益点是迁移可靠性、响应式查询与事务，而非性能（数据量均为数百条）：

1. **迁移**——现状 `onUpgrade` 是 `DROP TABLE`，任何结构演进都会丢数据；Room 的 `Migration` 是声明式的、可测的；
2. **响应式**——`Flow<List<...>>` 直接驱动界面，避免手写 `MutableStateFlow` + 提交逻辑在多表后必然出现的漏刷新；
3. **事务**——批量写入缓存与健康度需要原子性，SharedPreferences 无此能力。

**替代方案**：手写统一 `SQLiteOpenHelper`（多表 + 手写迁移 + 手写 Flow）。成本更低，但迁移与响应式两块要自己维护，且随表数量增长线性劣化。仅在「不做收藏 + 缓存只留首页一张表 + 不做后台刷新」同时成立时才回退到此方案。

**代价**：引入 KSP 注解处理器，构建变慢且与 Kotlin 版本耦合；实体与领域模型需分层映射。

### D2 持久化技术只出现在数据层，接口留在领域层

领域层定义纯接口（`WatchHistoryGateway` / `FavoriteGateway` / `CacheGateway` / `CatalogGateway`），数据层提供 Room 实现。

**理由**：保持 `domain/**` 无 Android 依赖，使领域层可继续用 JVM 单测与假实现验证；领域模型不因存储方案变化而重写。

**规则**：要查询的用结构化列，要整块取用的用 JSON 载荷——这条准则决定每类数据是拆表还是存载荷。

### D3 缓存读取显式区分三态

缓存读取返回「新鲜 / 陈旧可刷新 / 已过期」三种语义而非单纯数据。

**理由**：界面需要据此决定是否显示加载占位。若不区分，「先清空再填充」几乎必然发生，直接违反「卡片不跳动」的既有契约。

**配套**：后台刷新完成后比较内容标识，标识一致则不重建列表，仅替换变化部分并保持滚动锚点。

### D4 三类失效机制并存

签名型（来源集合变化）、前缀型（来源或分类级失效）、版本型（缓存模型版本）三类机制同时保留。

**理由**：只做 TTL 会漏掉「源刚被删除但缓存仍在展示」；只做签名会漏掉「分类内容更新」；只做版本无法处理运行期事件。三者互补，缺一即出现陈旧数据。

### D5 播放地址不落盘

目录与缓存均不保存播放地址，播放时按「来源 + 影片 ID + 线路 + 剧集」实时解析。

**理由**：CMS 播放地址普遍具有效期且与来源健康状态绑定，落盘会得到「点了播不出来」的体验，比不缓存更差；同时避免地址泄露到备份文件。

**代价**：每次播放多一次解析请求（可在详情解析时顺带取得，无需额外往返）。

### D6 内容目录只存元数据，采集增量且按优先级

目录保存标题、归一化片名与别名、封面、来源清单、线路与集名；采集按「当前播放下一集 → 首页目录 → 已搜未看详情 → 健康巡检」四级优先级调度，跳过有效期内条目。

**理由**：参考项目把全量采集放在服务端（常驻进程、共享带宽、统一出口），端侧不具备同等条件；分层后获得全量方案的主要收益（离线可用、搜索即时）而无存储与封禁代价。

**替代方案**：全量常驻采集 —— 因存储（数百 MB~GB）、带宽（数 GB）、耗时（数十分钟）与上游封禁风险被否决。

### D7 后台采集与用户请求配额隔离

后台采集并发 1–2、每来源每小时请求量受限，且不得占用用户触发的扇出预算；用户请求发生时后台采集主动降速。

**理由**：二者共享同一出口与同一批公共免费源。采集挤占前台预算会让搜索变慢，是最容易被忽略的退化路径。

### D8 搜索改为本地索引优先，扇出降级为回退

先查本地索引并立即返回，再由后台补采缺失来源；本地无命中时回退为原有并发扇出。

**理由**：搜索是全应用唯一每次都打满全部来源的路径，也是延迟与上游压力的主要来源。改为本地查询后响应从秒级降到毫秒级，且结果完整性不再受最慢源拖累。

**代价**：结果语义变化（本地结果可能不完整），需要在规格中显式定义，并接受「后台补全后追加」的行为。

### D9 收藏以归一化片名为唯一键

收藏主键为归一化片名，与聚合层共用同一归一化函数；收藏不强制绑定来源。

**理由**：若主键为「来源 + 影片 ID」，同一部片在多个来源会产生多条收藏。归一化函数若在两处各自实现，会随时间漂移导致去重失效，故必须共用同一实现。

### D10 观影记录权威键改为「来源 + 影片 ID + 线路 + 剧集」

播放地址降级为当次播放快照；新增归一化片名字段以支持跨源聚合。

**理由**：现状键为「来源 + 影片 ID + 线路 + 剧集」，但播放地址在键的兜底分支中参与身份判定，导致同一集在不同地址下重复计数。

**代价**：跨源聚合依赖归一化片名，对同片异名的识别能力弱于来源内精确匹配，属于可接受的折中。

### D11 引入 WorkManager 的范围限定为订阅同步

仅订阅源同步使用 WorkManager 周期任务；其余后台刷新走应用内协程。

**理由**：TV 应用不常驻，前台刷新用 WorkManager 只增加延迟；订阅同步是用户明确配置的持久行为，需要在应用被杀后仍能执行。

### D12 结构化数据与负载型缓存分表存储

`watch_record` / `favorite` / `source_health` 等用列存储以便查询与排序；`http_cache` 用 JSON 载荷存储整块响应。

**理由**：见 D2 的准则。二者生命周期与失效逻辑不同，合表会让清理与失效规则互相干扰。

## Risks / Trade-offs

- **[KSP 与 Kotlin 版本不匹配导致构建失败]** → 任务 1.1 以最小 PR 先行验证，未通过则回退 D1 的替代方案。
- **[迁移丢失历史与收藏]** → 显式 `Migration` + 迁移测试 + 保留旧 SP 原件一个版本；禁止破坏性迁移。
- **[实体与领域模型漂移]** → 载荷型实体统一用序列化注解，领域模型序列化契约有单测锁定。
- **[后台采集被上游判定为爬虫导致源被封]** → 配额限流 + 优先级让路 + 请求特征贴近真人 + 采集失败计入健康度并自动降级。
- **[后台采集挤占前台带宽导致搜索变慢]** → 配额隔离（D7）+ 用户请求优先 + 采集可暂停。
- **[本地索引结果不完整被误认为“没有该片”]** → 结果区标注来源数量并允许后台补全；规格中显式定义结果语义。
- **[缓存表无限增长]** → 有效期清理 + 总量上限 + 按种类与保存时间索引淘汰。
- **[Room 实体层导致 domain 泄漏 Android 依赖]** → 以自动化断言检查 `domain/**` 无 `androidx.room` 与 `android` 导入。

## Migration Plan

1. **准备**：引入 Room 与 KSP，建立空数据库与全部实体、索引，不接管任何读写。
2. **双读**：读路径先读旧 SP 与旧 `feed_cache`，转换为新实体后返回，保证行为不变。
3. **双写**：新写入同时落到新库与旧载体（仅在迁移窗口内保留）。
4. **回填**：一次性把 4 个 SP 文件与 `feed_cache` 旧表的数据迁入新库，并置迁移标记；旧数据保留一个版本。
5. **切换**：读路径切到新库，停止旧载体写入。
6. **清理**：下一个版本移除旧载体与双读代码。

回滚策略：任一阶段异常时把迁移标记复位即可回到旧读写路径，旧数据全程未被删除。

## Open Questions

- 目录缓存的硬过期时长与「内容可能已过期」提示阈值，取值需结合真实使用反馈，可在实现期调整，不影响规格语义。
- 搜索本地索引是否引入中文分词，取决于实际标题形态，可在实现期用真实数据评估，不影响索引契约。
