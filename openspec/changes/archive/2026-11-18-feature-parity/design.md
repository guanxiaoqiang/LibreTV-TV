# Design

> 配套：需求见 `specs/**`；动机见 `proposal.md`；参考项目对照见 [`../architecture-refactor/benchmark.md`](../architecture-refactor/benchmark.md)。
> 依赖：`architecture-refactor`（接口层与领域模型分层）、`local-first-storage`（持久化层与存储键集中化）。

## Context

当前源管理是「一次性快照 + 手工增删」：`assets/sources.json` 内置 30 个源，用户只能逐个添加或删除 URL。由此产生三个问题：

1. **源会失效，但只能手工一个个试**——采集站寿命短，失效是常态；
2. **换源必须更新 APK**——对无应用商店分发的自用项目成本高；
3. **观影体验缺少高频能力**——片头片尾跳过、备份迁移。

参考项目在服务端聚合场景已跑通订阅同步、跳过标记、TVBOX 解析与备份导出，其**语义与边界可借鉴**，实现需重写为端侧形态。

## Goals / Non-Goals

**Goals**

- 用户填一个订阅地址即可周期自动换源，无需更新应用；
- 支持导入社区通用的 TVBOX / SourceList 配置；
- 源列表、设置与观看历史可导出导入，支持换机迁移；
- 播放中可标记片头片尾并自动跳过；
- 所有新增能力在离线状态下仍可读取本地数据。

**Non-Goals**

- 不做直播 / IPTV / XMLTV EPG（定位不同，另开项目）；
- 不做鉴权、SSRF 防护、反向代理（端侧直连无此风险，但订阅地址仍需基本校验）；
- 不做 PWA / 双主题（不适用于 TV 客户端）；
- 不做「发布为链接」公开粘贴（会公开暴露源列表）；
- 不在本变更内实现收藏记录（已归入 [`../local-first-storage/`](../local-first-storage/) 的 `favorites` 能力）。

## Decisions

### D1 订阅源以远端为准，手工源不受影响

订阅引入的源以远端内容为准，下次同步会覆盖用户对该源的手工编辑；用户手工添加的源不参与同步覆盖。

**理由**：订阅的意义在于「以远端为唯一真相」，否则用户每次同步都要处理冲突，复杂度与收益不成比例。为降低困惑，源列表按归属分组展示，订阅源标记为「由订阅管理」，编辑时明示会被覆盖。

### D2 同步仅在前台执行，单次上限五个、并发二

**理由**：TV 应用不常驻，后台定时同步的收益远低于其带来的电量与流量成本；参考项目同样只在前台检查。设上限避免一次同步拉取过多条目拖慢首屏。

**代价**：应用长期不打开时订阅不会更新。

### D3 连续失败三次自动暂停，手动成功或改周期后恢复

订阅连续失败三次后状态转为「已暂停」，不再自动重试；手动同步成功或修改刷新周期时失败计数清零并恢复。

**理由**：订阅地址失效（404、域名过期）是常态，无限重试既无收益又持续消耗流量。暂停把「不可用」显式暴露给用户，由用户决定是否更换地址。

### D4 订阅内容解析：SourceList v2 与裸数组，TVBOX 另走导入通道

订阅地址按 LibreTV `SourceList` v2（`sources[]` / `liveSources[]`，仅取 `sources`）与裸数组解析；TVBOX / SourceList 格式的配置文件走独立的「导入」通道而非订阅。

**理由**：两者的语义不同——订阅是「持续同步的来源清单」，导入是「一次性并入现有列表的文件」。混用会让归属关系无法判断。直播条目在点播定位下忽略。

### D5 导入只接受符合 Apple CMS 特征的条目，且必须预览后确认

Spider 引擎、XML 接口、不可直接调用的外链 JSON、Base64 与压缩包装的分享链接、多仓 `urls` 顶层结构一律跳过；TVBOX `lives` 忽略。

**理由**：这些条目在端侧无法直接调用，强行导入只会产生永远失败的源，污染列表并拖慢每次扇出。预览让用户知道被跳过了什么，避免「导入了却不能用」。

### D6 跳过标记以归一化片名为键复用，且与广告过滤优先级固定

标记类型含片头结束点、片尾起点与中段区间；键为归一化片名，与聚合层共用同一归一化函数，实现上归入 `local-first-storage` 的持久化层。

**理由**：按「来源 + 影片 ID」标记则换源即失效；按归一化片名才能跨源跨集继承。广告过滤是源侧自动行为，优先于用户侧手动标记；同时提供全局开关以应对误伤。

### D7 备份包含版本号，导入按版本兼容并预览差异

导出内容含源列表（含订阅配置）、应用设置与观看历史，带 `version` 字段；导入时按地址合并去重，观看历史默认不覆盖。

**理由**：带版本号才能在格式演进后继续导入旧备份。默认不覆盖历史是保守默认——历史是用户资产，误覆盖不可接受，而漏覆盖可通过手动清空补齐。

### D8 收藏记录不在本变更实现

收藏的存储实体、主键规则与列表页交互归入 [`../local-first-storage/`](../local-first-storage/) 的 `favorites` 能力，本变更只负责把收藏纳入备份包。

**理由**：收藏依赖统一持久化层（见该变更 D1/D2），提前在旧存储上实现会产生二次迁移。

## Risks / Trade-offs

- **[订阅地址指向非法或内网资源]** → 仅接受 HTTP/HTTPS，拒绝回环与保留地址段；端侧由用户自担风险，但在界面明示来源与风险。
- **[订阅同步覆盖用户手工修改]** → 按归属分组展示并提示会被覆盖；手工源完全不受影响。
- **[自动换源导致用户不知情]** → 顶部短暂提示「已切换到 <源名>」，并始终提供手动选源入口。
- **[跳过标记误伤正常内容]** → 标记默认按归一化片名复用而非全局生效；提供一键撤销与全局关闭。
- **[导入产生大量不可用源]** → 导入前预览、跳过规则明确、按地址去重与数量上限；不可用源会由健康状态机自动降权。
- **[备份含播放地址造成泄露]** → 备份只含源、设置与历史，不含任何播放地址与本地缓存。

## Migration Plan

新增能力均为增量：订阅、导入、跳过标记与备份都是新数据项，不改动既有源列表与历史结构。仅当 `local-first-storage` 落地时，源列表、设置与历史需要从旧存储迁入新库——该迁移由该变更负责，本变更在其之后叠加即可。

回滚策略：各新增能力互相独立，可单独关闭（订阅可删除、跳过标记有全局开关、导入为一次性操作），不影响既有功能。

## Open Questions

- 订阅地址是否需要支持需要鉴权的场景，当前按不支持处理；若用户反馈存在此类订阅，可作为后续增量。
- 备份文件是否需要兼容既有第三方备份格式，当前仅支持本应用自身格式；如需兼容可在实现期评估。
